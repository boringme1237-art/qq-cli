# QQNT 本地数据库格式笔记

本文记录 qq-cli 开发过程中实测验证的 QQ NT（Windows 桌面版）本地数据库格式要点，
供后续维护者与同类工具开发者参考。部分知识来自社区公开研究（见文末参考），实测环境为
QQ 9.9.20.37051 (Windows x64)。

## 文件布局

```
Documents\Tencent Files\<QQ号>\nt_qq\nt_db\
  ├─ nt_msg.db          消息主库（群消息 + 好友消息 + 会话列表 + uid映射）
  ├─ group_info.db      群信息（群列表、成员、群精华、公告）
  ├─ profile_info.db    好友资料
  └─ ...（emoji/misc/fts 等）
```

**加密布局**：每个 `.db` 文件 = `1024 字节 QQ 私有头` + `SQLCipher 4 正文`。
正文第 1 页前 16 字节为盐（salt），之后才是加密数据。文件大小满足
`(size - 1024) % 4096 == 0`。

## 密码学参数

- 算法：SQLCipher 4 变体 —— AES-256-CBC 页加密 + 每页 HMAC 校验
- 密钥：16 字符**可打印 ASCII 口令**（非 hex 原始密钥），仅存在于运行中的 QQ.exe 内存
- 派生：
  - `enc_key = PBKDF2-<kdf_hash>(口令, salt, 4000, 32)` —— **kdf_iter 实测恒为 4000**
  - `mac_key = PBKDF2-<kdf_hash>(enc_key, salt ^ 0x3A, 2, 32)`（fast_kdf_iter=2）
- 页 HMAC：`HMAC-<hmac_alg>(mac_key, 加密数据 + IV + 页号uint32_le)`，
  存储于页尾

### ⚠️ 三个最容易踩的坑

1. **1024 字节头**：不剥离直接把文件当 SQLCipher 库打开/校验，永远失败。
2. **保留区取整**：页尾保留区 = IV(16) + HMAC 摘要，**必须向上取整到 16 字节倍数**：
   `hmac_sha1 → (16+20)=36 → 48 字节`（IV 在 [页大小-48, -32)），`sha512 → 80`，
   `sha256 → 48`，`hmac 关闭 → 16`。按 36 处理是常见错误。
3. **算法组合不固定**：页 HMAC ∈ {none, sha1, sha256, sha512} × KDF 哈希 ∈
   {sha1, sha256, sha512}，共 **12 种组合**，不同库/版本会混用，需暴力匹配
   （每种组合用第 1 页 HMAC 验证，毫秒级）。

## 密钥内存特征（提取用）

- 锚点：字节序列 `\x09HMAC_SHA1`（长度前缀字符串），编解码上下文把它与密钥
  相邻存放
- 密钥窗口：**16 字节**、全部可打印非空格（0x21–0x7E）、**不全为字母数字**、
  且 **16 字节地址对齐**
- 两条搜索路径：每个锚点 ±0x200 邻域按 16 字节步进找最近合格窗口；
  以及"密集锚点带"（≥4 个锚点、间隔 <0x4000）中心向外 ±0x20000 收集候选
  （Electron/V8 布局下密钥可能远离单个锚点）
- 候选按字符类别数（数字/大写/小写/符号）降序 + 出现次数排序后逐一校验

## 主要表与列（数值列名）

### nt_msg.db

| 表 | 用途 |
|---|---|
| `group_msg_table` | 群消息 |
| `c2c_msg_table` | 好友消息 |
| `recent_contact_v3_table` | 会话列表 |
| `nt_uid_mapping_table` | uid(u_...) → QQ号 映射 |

关键列（群消息与好友消息同构）：

| 列 | 含义 |
|---|---|
| `40001` | 消息 id |
| `40011` | 消息类型（2=文本/混合, 9=引用回复 …） |
| `40020` | 发送者 uid（`u_...`） |
| `40027` | 会话归属（群消息=群号；好友消息为标志值） |
| `40030` | 对方 QQ 号（好友消息=对方；群消息=群号） |
| `40033` | 发送者 QQ 号 |
| `40050` | 时间戳（unix 秒；少量脏数据为 0） |
| `40090` | 群名片 |
| `40093` | 昵称 |
| `40800` | 消息体，**protobuf**（数值即字段号） |

`40800` 消息体：外层为 protobuf，文本消息可递归解析出若干 UTF-8 片段
（@提及的 uid、完整渲染文本、分段文本等）；取"最长人类可读片段"通常即完整文本。
图片消息常表现为 `/gchatpic_new/...` 路径，文件消息为 `/download?...`，
群系统提示为 `<gtip ... txt="..."/>` XML。

`recent_contact_v3_table`：`40010`=会话类型（2=群）、`40021`=对方
（群号串或好友 uid 串）、`40094`=会话名、`40050`=最后消息时间、`40093`=最后发送者。

### group_info.db

| 表 | 关键列 |
|---|---|
| `group_list` | `60001`=群号, `60007`=群名, `60006`=成员数, `60005`=上限, `60004`=群主, `60022`=我的群备注 |
| `group_member3` | `60001`=群号, `1002`=QQ号, `64003`=群名片, `20002`=昵称（仅缓存部分活跃群） |

### login.db（全局，账号无关）

表 `login_table`，列 `"1000"`=uin、`"1001"`=uid、`"1007"`=昵称。该库使用
客户端内置的固定口令加密（见 x_key_scanner 源码），可用作解密实现的校准基准。

## 其他实测备注

- 同一账号下大多数库共用同一口令；个别库（guild1/rdelivery/yffm/recent_contact）
  密钥独立或无意义，不影响核心数据。
- `-wal` 文件同样可能带 1024 字节头（用 WAL 魔数 `37 7f 06 82/83` 探测偏移），
  帧内页面与主库同样加密，按页号回放即可得到最新明文副本。
- Live 库存在 `-wal/-shm`，工具应复制+回放而非直接打开源库。
